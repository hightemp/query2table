# Query2Table — чек-лист улучшений

Дата: 20 сентября 2026 года.

Основное направление: достоверность данных и надёжность длительных поисков. Основные задачи перечислены в порядке приоритета. Отмечать пункт выполненным только после реализации и проверки результата.

## Основные задачи

- [x] **1. Исправить дедупликацию — критично.**

  Исправлено: группы связаны с ID конкретных строк. Объединение выполняется одной транзакцией: сохраняется ID первой строки группы, переносятся все источники и связи с загруженными страницами, удаляются только дубликаты этой группы. Остальные сущности и другие запуски не изменяются. Пустые поля дополняются без потери нулей и `false`.

  Живая таблица и открытые детали синхронизируются с сохранёнными результатами, в том числе при отмене сразу после объединения. История и экспорт читают те же строки. Проверены чередующиеся группы, сохранность источников, откат транзакции и события интерфейса. Ранее перезаписанные данные автоматически восстановить нельзя — нужен повторный поиск.

  Реализация: [pipeline.rs](src-tauri/src/orchestrator/pipeline.rs), [repository.rs](src-tauri/src/storage/repository.rs), [control.rs](src-tauri/src/orchestrator/control.rs).

- [ ] **2. Строго проверять условия запроса.**

  Год, страна, отрасль и диапазон сумм должны проверяться перед добавлением строки. Сейчас извлечение получает схему колонок, а валидатор проверяет главным образом заполненность, типы и confidence. Нужно передавать ограничения запроса в извлечение и проверять соответствие результата этим ограничениям.

  Для неоднозначного «стартапы из 2024» стоит показывать интерпретацию: основаны в 2024 или участвовали в YC в 2024. Пользователь должен понимать и при необходимости уточнять, по какому условию программа отбирает данные.

- [x] **3. Сделать расчёт расходов достовернее.**

  Удалены вымышленные количества токенов и общий тариф. Каждая попытка LLM или поиска учитывается отдельно, включая повторы, резервного провайдера, ошибки с данными об использовании и отмену. Приоритет имеют списания, возвращённые провайдером; иначе используются фактические токены и тариф конкретной модели. Учтены кэшированные токены; thinking не оплачивается повторно поверх output.

  OpenRouter получает резервные тарифы из каталога моделей, Ollama Cloud — из опубликованных цен с учётом распознанных периодов пиковой нагрузки. Оценка расхода кредитов Ollama явно отделена от фактического денежного платежа. В Settings добавлены ручные тарифы для конкретного провайдера, адреса и модели, а также отдельные цены Brave и Serper. Неизвестная стоимость отличается от явно заданного нуля.

  В Query и History показываются списания, оценки, неизвестные расходы, токены и разбивка по моделям. Учёт сохраняется при завершении, ошибке и Cancel, даже без результатов. Денежный лимит проверяется перед каждым новым запросом во всех четырёх режимах. Уже отправленные запросы и неизвестные списания могут превысить отображаемый лимит; это объясняется в интерфейсе. Для строгого ограничения платежей нужны лимиты на стороне провайдера.

  Реализация: [BudgetTracker](src-tauri/src/orchestrator/budget_tracker.rs), [учёт попыток](src-tauri/src/providers/accounting.rs), [тарифы моделей](src-tauri/src/providers/llm/pricing.rs).

  Проверка пунктов 1 и 3: 265 Rust-тестов, 81 frontend-тест, 40 браузерных проверок Chromium/WebKit; Svelte без ошибок и предупреждений; frontend- и Rust-сборки, `git diff --check`. Отдельно проверены публичные тарифы Ollama без вызова модели и сохранение настроек/вывод расходов в настоящем Tauri WebView на синтетических данных. Версия не изменялась.

- [ ] **4. Подтверждать каждое важное значение.**

  Для суммы финансирования, имени CEO и даты сохранять ссылку, подтверждающий фрагмент и дату актуальности. Различать состояния «найдено в источнике», «предположено моделью» и «не найдено».

  Неизвестная сумма должна оставаться неизвестной, а не превращаться в ноль. Подтверждения должны относиться к конкретным значениям, чтобы пользователь мог проверить каждую важную ячейку.

- [ ] **5. Продолжать работу после закрытия приложения или сбоя.**

  Сохранять очередь запросов, обработанные страницы и текущий этап. Добавить продолжение исследования из истории после перезапуска приложения с сохранением уже выполненной работы и затрат. При восстановлении не выполнять повторно успешно завершённые операции.

- [ ] **6. Дозаполнять отдельные строки и поля.**

  Дать возможность выделить компании без CEO и нажать «Найти недостающие данные». Аналогично — перепроверить сомнительную сумму или обновить устаревшие сведения. Повторный поиск должен работать с выбранными строками и полями, сохраняя остальные результаты.

- [ ] **7. Расширить работу с таблицей.**

  Добавить изменение ширины, порядка и видимости колонок, закрепление первой колонки, редактирование с отменой, выделение строк и экспорт выбранных или отфильтрованных результатов. Для чисел предусмотреть разделители разрядов, валюты и единицы измерения.

- [ ] **8. Добавить измеримые проверки качества поиска.**

  Подготовить набор контрольных запросов и сохранённых страниц с ожидаемыми результатами. Проверять соблюдение условий, пропуски, дубликаты и подтверждённость значений. Использовать эти проверки при изменении модели, промптов и логики обработки данных.

## Дальнейшие возможности

- [ ] **Шаблоны исследований.**

  Сохранять повторно используемые запросы, схемы колонок, ограничения и настройки запуска, чтобы быстро выполнять однотипные исследования.

- [ ] **Сравнение повторных запусков.**

  Показывать новые и исчезнувшие сущности, а также изменения отдельных значений между запусками одного исследования. Сохранять связь изменений с датами и источниками.

- [ ] **Обработка страниц, требующих JavaScript.**

  Добавить получение содержимого через браузер для страниц, на которых обычный HTTP-запрос не возвращает необходимые данные. Сделать использование такого режима явным, учитывая дополнительное время и ресурсы.

- [ ] **Резервное копирование и восстановление.**

  Добавить создание и восстановление согласованных копий локальной базы с настройками, историей и результатами. Для работающей базы использовать механизм резервного копирования SQLite.

  Документация: [SQLite Backup API](https://www.sqlite.org/backup.html).

- [ ] **Обновление приложения с проверкой подписи.**

  Добавить проверку доступности новой версии, показ изменений и установку обновления из интерфейса приложения. Проверять подпись обновлений перед установкой.

  Документация: [Tauri Updater](https://v2.tauri.app/plugin/updater/).
